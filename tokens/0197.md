# BRC-197: Accumulating Right-of-Sale Listings and Purchase Orders

Ty Everett (ty@projectbabbage.com)

## Abstract and status

This proposed contract represents a reusable sale listing by a UTXO. A buyer can spend it without a new seller signature if the transaction recreates the listing and increases its value by exactly the purchase price. The transaction also records a recipient-bound purchase. The asset may be access to content, an entitlement or another application-defined item; this contract specifies purchase accounting and lineage, not the asset's business meaning or delivery method. A private overlay can use the purchase with BRC-196, but an overlay or a particular application is not required to interpret the on-chain transition.

The proposal specifies transaction predicates, receipt bytes, lineage and optional administrative operations. A conforming Script implementation MUST enforce the stated Script predicates in Bitcoin, not merely emulate them in a topic manager. Compiler choice is deliberately separate: an installed script-family adapter must identify exact executable bytes, compiler/artifact version and verification results before a wallet or overlay can accept that family. The existence of this specification or a passing arithmetic fixture is not evidence that a compiler output is safe.

## 1. Immutable listing descriptor and lineage

Represent the descriptor as BRC-192 canonical JSON, using its digests and encodings:

```typescript
type ListingDescriptor = {
  version: 1; chain: Chain; assetId: Hex32; seller: Identity;
  lineageAnchor: Outpoint; purchasePrice: U64; reserve: U64;
  termsDigest: Hex32; scriptFamily: string;
  administration: 'none' | 'seller-v1';
  metadataDigest: Hex32
}
```

Price and reserve are positive and all values fit BRC-100's SatoshiValue range (at most 2100000000000000 satoshis). The anchor's chain MUST equal the descriptor chain and the verifier's configured chain. A zero-price promotion uses a different explicit profile. `termsDigest` commits to the frozen purchase terms and `assetId` to an immutable asset description under a declared domain schema. `metadataDigest` commits to versioned asset metadata. A content licensing profile may use BRC-170 asset and offer identifiers; this base contract neither requires that schema nor assumes every asset is encrypted media.

The descriptor is immutable within one lineage. Changing price, terms, seller, asset or administration requires a new lineage and explicit catalogue supersession; no silent retroactive change to prior purchases. `listingId = digest("sale-listing", descriptor)`.

The genesis transaction consumes `lineageAnchor` at input zero and creates exactly one listing at output zero with value `reserve`. A seller-signed BRC-192 object of type `sale-genesis`, body `{version:1,listingId:Hex32,genesis:Outpoint}`, authorizes the exact genesis outpoint. Authority to provide the asset is validated under the selected domain policy independently of this signature. The descriptor includes the already existing anchor, avoiding a circular commitment to its own genesis txid.

Every accepted descendant MUST have a verified path of permitted transitions back to that exact genesis, including all predecessors of a merge. A copied locking script, matching asset ID, or matching genesis string is not lineage proof. This ancestry check is a domain-admission/buyer obligation. The Script predicates preserve successors of real listing spends but do not magically prevent unrelated parties from creating lookalike outputs. If bounded ancestry verification cannot finish, the listing is unresolved, not accepted by assumption. Retained validated checkpoints may accelerate verification only under an explicit trust policy.

## 2. Script-family boundary

An installed family provides deterministic `encode(descriptor) -> lockingScript`, exact inverse parsing, purchase/admin unlocking construction and independent validation. One descriptor maps to one exact locking script within that family version. Alternative compilers or optimizations that change bytes use a different family identifier. Nodes and clients MUST reject unknown families before purchase or admission. A fetched description or seller signature alone cannot install trusted executable validation logic.

The required transaction introspection uses a sound [BRC-21](../scripts/0021.md) preimage construction or an equivalently validated Script technique. It MUST bind the current input outpoint, amount and full scriptCode; complete prevout and sequence hashes; transaction version/locktime; and the hash of all outputs, with `SIGHASH_ALL | SIGHASH_FORKID` (`0x41`). Neither `SINGLE`, `NONE` nor `ANYONECANPAY` is accepted for the covenant introspection. Every supplied serialization is parsed completely with canonical Bitcoin lengths and no trailing bytes; recomputed hashes must equal the bound preimage. Merely pushing an alleged preimage into Script is insufficient.

For the mandatory purchase route, the current outpoint MUST equal the first serialized input outpoint. Bitcoin's no-duplicate-input rule makes this unambiguous without trusting an alleged input index. Another listing cannot satisfy this same purchase route in a later input. Funding inputs follow input zero. Inputs use final sequence `0xffffffff`, transaction locktime is zero, and transaction version is 1 or 2 as explicitly supported by the family. This profile does not use interim/non-final purchases to release keys.

## 3. Mandatory permissionless purchase

The transaction MUST have one listing input at index zero, at least one external funding input, a successor at output zero and a purchase receipt at output one. Further outputs are buyer change or explicitly authorized unrelated funding outputs; they MUST NOT be counted as listing successors. The successor's locking script is byte-for-byte identical to the consumed listing and its value is exactly:

```text
successorValue = previousValue + purchasePrice
```

The receipt value is zero. Price must not be deducted from the old listing, reused as its fee, or counted twice. Funding inputs supply the price and transaction fees; ordinary Bitcoin input/output conservation applies. The covenant enforces the successor and receipt layout and rejects overflow. It does not require the seller to sign this purchase. The funding wallet still authorizes its own inputs through BRC-100.

Output one's locking script is `OP_FALSE OP_RETURN` followed by one minimally encoded data push containing exactly these bytes:

```text
ASCII("ROSL")           4 bytes
version                 1 byte, 0x01
operation               1 byte, 0x01 for purchase
listingId              32 bytes
acquisitionId          32 bytes
requestDigest          32 bytes
recipient              33 bytes, compressed secp256k1 identity
termsDigest            32 bytes
```

Total payload length is 167 bytes. Hex digests decode directly into their 32 bytes, without txid byte-order reversal. `listingId` and `termsDigest` MUST match the consumed descriptor. The recipient key must be structurally valid. Acquisition ID is a caller-selected 32-byte identifier and request digest commits to the domain's canonical purchase request; its schema MUST be declared by the fulfillment profile. When BRC-196 is selected, both fields instead use its exact preparation derivations. The covenant binds the receipt bytes to the spending transaction; the fulfillment service separately verifies request and recipient authority. A recipient's public identity becomes linked to the purchase; a future privacy profile must specify its alternative explicitly.

In this base route, price increments are the state: the locking script need not mutate merely to accumulate proceeds. For price 1000 and initial value 1, successive purchases produce 1001 then 2001 satoshis. A valid purchase transaction can survive even if its buyer never retrieves the key, which is why recovery is separate from catalogue currentness.

## 4. Optional seller administration

`administration=none` enables only purchase. `seller-v1` additionally enables split, merge, payout and retire. All administrative listing inputs MUST verify the seller's Bitcoin transaction signature with `0x41` over their own bound preimages, as well as the route's covenant checks. The signature must be by the descriptor's seller key, not an untrusted key supplied with the unlock. A wallet must explicitly support this authority or use a separate future admin-key profile; it must not export its identity secret as a workaround.

Each administrative transaction has `m` listing inputs first, with no repeats, and `n` listing outputs first, followed by one zero-valued operation receipt and any separately funded change. The receipt is the same prefix/size convention, but its data payload is `ASCII("ROSL") || 0x01 || operation || listingId || uint32le(m) || uint32le(n) || uint64le(payout) || destinationHash`, where `destinationHash` is SHA-256 of the payout output script, or 32 zero bytes if payout is zero. Operations are split `0x02`, merge `0x03`, payout `0x04`, retire `0x05`. Its exact payload length is 86 bytes. No acquisition is created by an administrative receipt.

Every predecessor has the exact same descriptor/locking script and independently verified lineage. Every continuing listing output has that same script and at least `reserve` satoshis. The caller supplies previous-output evidence for amount checks; Script MUST authenticate amounts and scripts against each referenced previous transaction/outpoint, not trust an uncommitted list of input values. Each covenant invocation proves its own current outpoint occurs exactly once among the first m bound prevouts, and checks the same receipt, m, n and complete output serialization. Previous transaction hashes and output indexes bind all claimed predecessor values to those actual prevouts. The domain validator verifies the whole transaction once and does not count a predecessor again when validating another output.

For split, `m=1`, `2 <= n <= 64`, payout is zero and continuing values sum exactly to the old value. Split therefore requires enough existing reserve for every new listing; funding a reserve expansion requires a separately specified profile. For merge, `2 <= m <= 64`, `n=1`, payout is zero and the new value equals the sum of all predecessors. Thus 2001 plus 3001 becomes 5002, without dropping either reserve or counting a predecessor twice. For payout, `m=n=1`, payout is positive, and `newValue + payout = oldValue`, with newValue at least reserve. For retire, `m=1`, `n=0`, payout equals the complete old value.

When payout is nonzero, a payout output immediately follows the receipt and has exactly that amount and the script matching destinationHash. The seller's signature authorizes that destination, which may itself be a distribution contract. This profile does not claim that a payout to one destination has already paid several beneficiaries. Distribution rules and accounting remain separately declared obligations. No administrative listing balance pays the transaction fee; external funding pays fees. For every route, `sum(listing inputs) = sum(continuing listings) + payout`, with checked arithmetic.

Split enables independently spendable sale chains, reducing on-chain input races when the catalogue assigns them to different buyers. It does not guarantee parallel throughput in an engine that serializes admission, and a catalogue cannot promise an input lock it does not control. Merge, retirement and payout can race purchases; all clients need exact-transaction recovery.

## 5. Overlay behavior, migration and assurance

When used with overlays, use distinct topic/lookup profile rules for these listings; do not reinterpret existing application tokens as covenants. A compatibility catalogue may expose old and new formats with explicit type tags. A stable application identity can link them, but only a new authorized genesis starts this covenant lineage. Preserve historic entitlements and acquisition recovery. Application-specific token conversion and user journeys belong in their own integration guides.

Admission verifies BEEF, Script, descriptor/family, genesis ancestry, operation shape and application rights. It emits a coherent spent/created group through BRC-193. The chosen private seller additionally verifies BRC-196 purchase association before releasing a key; replicated public nodes need not possess it. Reorganizations invalidate currentness and restore/recompute descendants according to evidence, without erasing issued acquisition records.

Conformance requires positive purchase, split, merge, payout and retire fixtures for each claimed route and rejection of underpayment, over-increment, changed successor script, missing/changed receipt, recipient/terms mismatch, duplicate or unrelated predecessor, cloned lineage, overflow, unsigned administration and fee extraction from listing balances. The release gate additionally requires real compiled locking/unlocking scripts executed by an independent Script verifier, wallet-funded transactions, negative mutation vectors, reproducible compiler/artifact hashes and review of introspection/input binding. [Packet arithmetic vectors](../overlays/media/0192-0199/README.md) test the economic predicates only; no compiled implementation is certified by this specification PR.
